# Architecture

## System shape

`Desktop Web / Mobile Web / iOS / Android / Docs` → `Cloudflare Worker API` → `Hyperdrive or CFPG Service Binding / Queues / R2 / CFsend` → `PostgreSQL-compatible data and provider services`

The always-running `starter-dev` container has only project, dependency and shared-provider-profile mounts. Docker Socket and Production SSH material exist only in the explicit `starter-ops` Compose profile used for scoped provisioning or Production operations.

Assembly control flow:

`product brief` → canonical `/setup` → ignored Factory Draft → deterministic source/target materialization → independent product `/setup` + Agent Map + receipt → local verification → Development release → explicit Production release

Product type and selected platforms control deployable surfaces before dependency locking and release. Web SaaS retains Marketing, Docs, Web App and Worker API, while Expo/Mobile output is added only when Mobile Web, iOS or Android is explicitly selected. Website/content retains Astro output (and Docs when selected) while pruning Worker, database, Cloudflare runtime and mobile source. Mobile App retains Expo and Worker API, with companion Astro and Web Admin controlled independently. Local `/setup` is tooling and does not imply a consumer Web output.

The generated product is operationally complete without an All2CF connection or mounted source checkout. Local `/maintenance` owns connection and update UX; `/all2cf` and `/update` are compatibility aliases. Codex prefers hosted All2CF MCP OAuth to obtain an expiring project-scoped connection receipt after ownership and paid-entitlement checks; manual receipt import is the non-MCP fallback. A missing linked source reports the installed receipt and unavailable update state without blocking local operation. Disconnect removes the ignored local credential immediately and revokes its remote token when the service is reachable; source, providers, database and deployment ownership are unchanged.

`.starter/materialization.json` is the Base ownership ledger for incremental updates. The materializer compares its recorded file hashes and dependency versions with Local and Target. Local-only deviations are recorded as overrides and skipped during application; Target-only changes are applied; simultaneous deviations fail closed. The apply phase snapshots every touched path in memory and restores it on failure. Automatic semantic conflict resolution and destructive database migration are outside this boundary.

The generated product always selects internal `foundation.core`, a curated list of Starter infrastructure such as Maintenance UI, local updater and materializer. Product business files are excluded. Before an Engine update, `starter-link` writes an ignored compressed recovery snapshot, verifies the current project, applies the candidate, then runs typecheck and build; failed verification restores the snapshot and leaves it available for manual recovery. Unselected Pack source remains absent and only its Catalog version advances.

`AGENTS.md`, `AGENT_MAP.md` and `CODEX.md` are product-owned, not foundation-managed files. Their customer routes and rules are never replaced as whole documents. Starter AI behavior evolves through `.ai/features.json`, generated `.ai/agent-map.json`, the user-level plugin and reviewed Change Specs; a structured identity collision must be reviewed rather than overwritten.

Generated registries use the same Base/Local/Target rule as Pack files. Wrangler configuration is merged by receipt-owned bindings, routes, queues, schedules, variables and required-secret declarations while preserving unowned entries. Environment values, secret files, project business code, native mobile directories and unregistered package scripts are never automatically owned. Case-insensitive collisions, symbolic-link traversal and concurrent mutation locks fail closed before application.

The functional Codex plugin follows the same independence boundary. One user-level `all2cf-project` installation detects generated repositories from `.starter/source.json`, `.ai/manifest.json` and `AGENT_MAP.md`; Factory output does not contain plugin source. Local project rules and commands remain authoritative, so missing or disabled plugin state never blocks installation, build, release or maintenance.

- `apps/marketing` is the static-first Astro public product site. Only Blueprint-selected Page Catalog routes are materialized; its default route output requires no client JavaScript.
- `apps/web` is a Desktop Web product optimized for mouse, keyboard, large-screen density, dashboards, tables, and complex operations. Its deploy artifact is mounted under `/_app`, while `/login`, `/app`, `/support`, `/admin`, and `/dp` ask the Worker asset binding for that shell.
- `apps/mobile` is a separate touch-first Expo Router product whose UI source targets Mobile Web, iOS, and Android.
- `apps/docs` is a static Astro/Starlight workspace. A collision-checked merge combines Marketing at the root, React under `/_app`, and Docs under `/docs` into one Worker asset artifact; it does not create another Worker or server runtime.
- Desktop and Mobile do not share pages, navigation, layout, UI components, or presentation tokens. They may share API/domain types, auth and permission contracts, i18n keys, telemetry events, and base brand assets.
- Mobile Web uses Expo Router's `single` output because it is an authenticated application rather than an SEO-oriented document site. Its hosting domain and release target remain undecided.

Project initialization replaces generic names and records the smallest accurate component map. Ownership, trust boundaries, and data flow remain explicit.

## Reusable SaaS foundation

The target baseline combines three audited responsibilities without importing their runtimes:

- Open SaaS supplies the standard SaaS product shell and flow inventory.
- SaaSBoard supplies authenticated Sidebar, Topbar, search, notification bell, account/plan state and Dashboard interaction references.
- LastSaaS supplies the completeness checklist for organizations, RBAC, billing, entitlements, usage, API keys, outgoing webhooks, telemetry, branding, announcements, system health and platform administration.

Better Auth and its official plugins own identity and available security/SaaS primitives. Cloudflare Workers, selectable Hyperdrive/native PostgreSQL or CFPG Service Binding access, Queues/Workflows/Cron, R2, CFsend and provider adapters own the runtime. Wasp, Prisma, MongoDB, Go/Fly and donor mock data do not enter the generated product.

The permanent Product Shell owns responsive navigation, global search seam, workspace switcher seam, notification bell/inbox, account/plan state, appearance, language, help and platform Admin entry. Dashboard, Settings, Support, Docs and Admin share this shell, permission model, notifications, audit registration and selected StyleKit system. Product-specific modules register their routes, navigation, events, permissions and Admin surfaces rather than replacing the shell.

## Configuration and knowledge boundaries

- `/setup` is the single local configuration route in both the canonical source and generated projects. In canonical source mode it writes an ignored draft and can generate a separate Git project without changing source identity; in a generated project it writes the reviewed Blueprint/config and refreshes `/dp`. It does not mutate Cloudflare or database infrastructure directly; deployed Workers reject `/setup` and `/__starter/*`. Legacy `/factory` requests redirect to `/setup` and are not a product surface.
- Universal visual intelligence is independently owned by `/opt/1panel/apps/visual`. Starter pins its cross-project contract in `integrations/visual.json`, declares `visual-design` as an external optional plugin, and records the requested state in `blueprint.visualIntegration`. `all2cf-project` does not own design search, Recipes, third-party visual catalogs or Visual MCP operations.
- The integration fails toward a Starter-owned baseline rather than blocking Factory. Runtime capability discovery is required before any MCP use, and a transport response never proves a profile was materialized. Starter retains Factory request construction, response validation, collision protection and local verification; the generated project owns its `.visual/` archive.
- PostgreSQL is the only database contract. Product-domain code selects SQL-first or Drizzle; both reuse `pg` and `createDatabasePool`. Hyperdrive and CFPG are transport bindings only, so CFPG never introduces separate queries, migrations, Drizzle schemas or commands.
- The `starter-dev` Compose service runs `npm run setup` as its supervised main process and restarts unless explicitly stopped. Port `15173` therefore owns both local `/setup` and the current-worktree `/dp`; `dev.logicm8.com/dp` remains the immutable Development release view and may intentionally lag local edits until the next Development release.
- Setup saves are explicit and step-scoped. Draft and continue actions persist before navigation, interrupted Vite reloads recover the saved review state, and final save remains on a visible completion screen. Provider credentials are write-only project-local development inputs: Setup reports readiness/source without returning values, while `/admin` reports runtime health read-only and directs changes back to local Setup.
- `/setup` records intent; it does not silently install packages. AI runs the read-only materialization plan, reviews collisions, then explicitly applies it. During deselection, the Blueprint may truthfully show `selected: false` and `materialized: true` until apply removes receipt-owned output. Pack manifests own exact files, page-specific files, dependencies, lazy client routes, exact Worker application routes, `assets.run_worker_first` entries, optional Better Auth server/client and Worker event registries, Queue producer/consumer declarations, and secret requirements. Generated target Design adapters and the Marketing project contract are also hash-tracked in `.starter/materialization.json` for drift detection.
- Catalog delivery is explicit: `baseline` is permanently present, `materializer` requires a matching receipt-backed pack manifest, and `planned` is informational only. Planned packs cannot enter a preset, a saved selected Blueprint, or a materialization run.
- `starter.blueprint.json` answers what this project selected and how far each selection has progressed.
- `catalog/catalog.json` answers what Starter can assemble and the contract for each pack.
- `catalog/providers.json` answers which Provider, infrastructure and release-platform options exist, which are currently selectable, and what credentials, Bindings, dependencies and verification each option owns. A visible Planned option is not an availability claim.
- The StyleKit source catalog and selected owned snapshot answer which style/revision is selected, its version and hashes, complete tokens/recipes/AI rules, and readiness of every Web, Marketing, Docs, and Mobile adapter.
- `pages/catalog.json` answers which complete PowerAI-derived page families and content models exist, which renderer owns each route, which routes are mandatory, and which source patterns were accepted, replaced or rejected.
- `starter.manifest.json` answers what the repository itself currently contains and supports.
- Markdown and Change Specs explain why the state exists. Generated `/dp` JSON is a disposable projection of these sources.
- `/dp` is read-only and reports selection, materialization, verification, release, and drift. `/admin` remains the authenticated product-operations area and never becomes the Starter configurator.

Each Catalog pack declares targets, ownership, provenance and license, update policy, routes or APIs, storage and bindings, dependency requirements, conflicts, performance budgets, tests, documentation, and removal behavior. Materialization omits unselected code and infrastructure instead of using broad runtime feature flags.

## Catalog ownership

- Baseline Design Catalog: the canonical source temporarily retains the previously verified StyleKit inventory as migration evidence, while Factory and generated projects expose and carry only one Starter-owned fallback profile. Universal catalogs and later visual directions belong to Visual.
- Page Catalog: owned complete route families and content models. PowerAI Astro is a pinned, licensed donor whose brand, fixed theme/content, auth behavior and unnecessary islands are rejected. Public marketing and growth content is static-first Astro; authenticated surfaces use React/shadcn; Docs uses Starlight.
- SaaS Catalog: a complete baseline shell and platform services plus selectable product capabilities. Open SaaS and SaaSBoard are pinned structure/interaction donors, LastSaaS is the coverage checklist, Better Auth is the upstream behavior owner where an official plugin exists, and the runtime is Cloudflare-native.
- Capability Catalog: independently selectable capabilities such as maps, charts, uploads, search, AI, realtime, queues, and observability. MapCN is the first locally verified Web pack; its adapted components become owned source while MapLibre remains a normal runtime dependency only when selected.
- Optional source templates live under `packs/` and are excluded from application imports. Generated client route, Worker route, auth-plugin, Worker-event and storage-adapter registries have no optional imports when no pack is selected. A capability route that sits outside the permanent application route families must explicitly declare `workerFirst`; materialization adds the exact route to both Wrangler environments and the Worker asset-shell registry, and removal deletes both. Object Storage adds its Worker/Web/SQL boundary plus either an R2 binding or the S3 SDK and secrets; MapCN adds only its map route/runtime; Organization adds its official server/client plugin adapters, empty-baseline SQL and product routes; Stripe adds its aligned SDK/plugin, empty-baseline SQL, billing route and release-secret contract; Outgoing Webhooks adds environment-derived Queue producer/consumer names and a signing-root requirement. Deselection removes only receipt-matching assets and refuses changed owned infrastructure declarations.
- Presets compose only executable Catalog IDs rather than duplicating implementations. The default `saas-foundation` preset includes identity, Product Shell, notifications, settings, support, Admin framework, Docs, audit, and health. TOTP 2FA remains a separately selectable Better Auth security pack. `api-saas` composes API Keys, Stripe Billing, Entitlements, Usage, Outgoing Webhooks and the Developer/API boundary with hard dependency checks. Organization, non-free charging, API Platform, storage, maps, and AI remain explicit product choices; `/setup` derives a visible proposal from `productIntent` without silently applying it.

`catalog/saas-sources.json` pins the Open SaaS, SaaSBoard, and LastSaaS revisions, license fingerprints, accepted source paths, rejected runtimes, Starter targets, and manual review policy. `catalog/saas-capabilities.json` maps every SaaS capability to its owner, delivery mode, status, routes, APIs, SQL schema, verification, and honest gaps. These files are machine-readable inputs to AI context and `/dp`, not prose-only promises.

## Decisions

- PostgreSQL access is SQL-first. No default ORM.
- Local development, schema migration, SQL, Drizzle, tests, backup/restore and ordinary database tooling always use the native PostgreSQL command contract. Hyperdrive and CFPG never create alternate local commands or migration files; most projects remain on the default native PostgreSQL path and do not install the optional connector.
- Database transport selection is environment-isolated. Development and Production independently choose native PostgreSQL through their own Hyperdrive binding or CFPG through the pinned All2CF client, Wrangler's `pg` alias and an `ALL2CF_DATABASE` Service Binding; application SQL remains unchanged. Setup validates and records a CFPG command only for an environment that selects CFPG and never runs npm or deploys. Materialization installs the connector when either environment needs it, changes only the selected environment, requires different database IDs when both select CFPG, and restores Hyperdrive when CFPG is deselected. Older Blueprints without `transports` retain their global `provider` fallback.
- Starter owns only the CFPG connection adapter: the pinned client dependency, `pg` alias, immutable install descriptor and `ALL2CF_DATABASE` Service Binding. CFPG database creation, schema migration execution, Database Worker lifecycle, concurrency and database readiness belong to the All2CF/CFPG product. Starter and its release controller must fail closed when that product has not supplied a ready connector deployment path; they must not recreate CFPG internals with temporary Workers or private migration protocols.
- Cloudflare facts and operations are verified through official Cloudflare MCP first.
- Generated projects accept two explicitly different preflight authorities: `official-cloudflare-mcp` for AI/local operation, and `all2cf-control-plane` only inside a trusted All2CF Runner using the organization's saved Owner connection. The latter never masquerades as MCP evidence and must retain the same target, collision, account, config-hash and freshness checks.
- An All2CF-managed Development release may adopt an existing Hyperdrive only after live database/user identity validation. Direct PostgreSQL credentials remain Runner-only for migrations and are not sent to the Worker.
- Worker Studio integrations are capability-detected at runtime.
- Durable state, queues, storage, and external services must document ownership and failure behavior.
- Object storage is optional and provider-neutral at the API boundary. PostgreSQL owns metadata; R2 or S3-compatible storage owns bytes. Server-derived user keys and metadata authorization prevent bucket/key authority from reaching clients. R2 uses distinct environment buckets through `OBJECTS`; S3 adds its SDK and distinct environment secrets only while selected.
- Release verification reaches the selected storage adapter through a fixed HMAC-protected route, compares exact generated bytes and deletes the generated key in `finally`. The proof is derived from the existing environment Better Auth secret, so no public test route or extra release credential is introduced. Post-deploy reconciliation records exact selected R2, Vectorize and Queue identities even when Wrangler performed automatic provisioning.
- Product Analytics is currently unselected. Pulse is the preferred future external-product owner of measurement and attribution; other analytics options remain Catalog references rather than bundled runtimes.
- Workers AI is an optional receipt-owned server capability. Selecting it adds the native `AI` Binding, environment model/Gateway variables, a bounded server helper and an Admin-only Binding test. It never creates a generic public inference endpoint; copied products own prompts, permissions, quotas, evaluation and retention.
- Search is capability-gated: `none` adds nothing, PostgreSQL reuses the SQL-first database, and Vectorize adds a distinct environment index Binding. Vector dimensions/metric are immutable and embedding-model-dependent; product ingestion, namespaces, metadata filters and retrieval evaluation remain product-owned.
- Native push is an optional mobile/Worker capability. Expo Push adds its SDK-compatible config plugin and dependency only when selected, obtains tokens against the active EAS project, stores devices per Better Auth user, and sends only from server-owned recipient context. Development and Production project IDs and credentials cannot cross lanes.
- SMS is a separate optional Worker capability. Twilio uses environment-isolated API keys and senders, reserves a SQL idempotency key before the external request, stores only recipient hash/last four and provider evidence, and exposes no arbitrary client-recipient send endpoint.
- Media separates bytes from transformations: Object Storage owns originals, optional Cloudflare Images owns bounded Worker-native resize/transcode, and video remains an independent Stream capability. No generic public transformation proxy is part of the Starter.
- Optional Stream creates short-lived direct-upload URLs from the Worker, stores provider UID under the Better Auth user, accepts state only through timestamped HMAC webhooks and returns public HLS/DASH URLs after readiness. API tokens never reach clients; private playback remains disabled pending signing-token support.
- Cron dispatches through the same generated Worker event registry as Queue handlers. Environment expressions are receipt-owned; deselection emits an explicit empty trigger array so remote schedules are removed on the next release. Product jobs remain separately registered and idempotent.
- Workflows uses a generated top-level class export plus environment-derived Binding/resource names. The release controller records the live resource and, after a future deselected deploy removes class/Binding references, deletes only that exact recorded Workflow. Product payloads, steps, rollback and retention remain copied-product decisions.
- Realtime rooms use one `StarterRealtimeRoom` SQLite-backed Durable Object namespace per Worker environment. Authenticated room requests proxy through Better Auth, and the object uses WebSocket Hibernation with attachment-restored user identity, a 1000-character frame cap and persisted monotonic sequence state. Deselecting removes the route, Binding and class export but deliberately emits no deletion tombstone; namespace data requires a later explicit product-owned destructive decision.
- Desktop Web uses shadcn/ui/Tailwind. Mobile Web/iOS/Android use a lean Tamagui 2 runtime configuration with package-level imports.
- Runtime baseline: Node 24, Astro 7.2.4, Wrangler 4.124.0, Workers types 5.20260820.1, Hono 4.13.3, Vite 8.2.2, Expo 57.0.14, and React Native 0.86.2. Expo owns compatible React, React Native, Router, and native-module selection.
- Better Auth 1.7.2 owns identity endpoints in the repository. It uses its built-in PostgreSQL/Kysely adapter through Provider-aware request-scoped pools, host-only Web cookies, official Expo deep-link/SecureStore plugins, the official Admin plugin, database rate limits, and an SQL-first initialization baseline. Every Starter project provisions separate new empty Development and Production databases from the final selected shape; legacy data migration, backfill, dual-write, and compatibility paths are outside Starter.
- Better Auth 1.7 account identity is keyed by `(issuer, account_id)`. The empty-project schema starts with this contract: credential rows use `local:credential` plus their linked stable user ID, while Google, GitHub and Apple rows retain their verified provider issuer and subject. Starter does not carry legacy-account backfill logic; an existing product must own its upgrade migration separately.
- Cloudflare Turnstile is an optional Better Auth Captcha pack, not a parallel authentication layer. When selected, separate environment site/secret key pairs protect exact credential sign-up, sign-in and password-reset endpoints; client tokens are always verified by Better Auth through Siteverify and missing or provider-failed validation fails closed.
- Better Auth core and every selected official plugin upgrade together on the latest reviewed stable-compatible line. Generated schema changes are proposals; the reviewed current SQL baseline remains the initialization source for new empty Starter databases.
- Version alignment is enforced offline across active package manifests, deselected optional-pack manifests, and official-plugin source revisions. Registry freshness remains a separate online report and never silently changes versions.
- Better Auth Organization is an optional tenant layer with teams and verified-email invitations. Its `owner`, `admin`, and `member` roles are organization-scoped and never imply the Better Auth platform Admin role.
- Better Auth API Key is an independently selectable machine-credential layer. The default pack creates user-owned, hashed, rate-limited keys with one non-escalating `product:read` permission and explicitly disables API-key-to-session conversion. A copied product must replace that placeholder permission vocabulary before Development release; organization ownership is never inferred from selecting both packs. The reviewed SQL baseline adds an owner foreign key and unique hash index beyond the generated proposal while preserving the plugin's field contract.
- Stripe Billing is independently selectable and user-scoped by default. It uses Checkout Sessions, Customer Portal, separate Test/Live secrets, verified email before upgrade, server-authorized reference IDs, official webhook signature verification, a unique subscription projection, and replay-counted webhook receipts. Organization billing is never enabled merely because both packs are selected; a copied product must explicitly choose its billing owner and authorization policy.
- Entitlements are a separate Starter-owned optional pack that requires Stripe Billing. The Worker derives the current user from the verified session, accepts only unexpired active/trialing subscription projections, resolves indexed SQL plan grants, and falls back to Free for missing, ended, invalid, or unknown plans. The generated Worker-feature registry installs and removes optional backend routes through the same materialization receipt; product server routes remain responsible for enforcing the resolved feature keys.
- Usage Metering is another independent optional pack above Entitlements. Completed product actions call a server-only helper; production clients receive read-only snapshots and cannot submit a subject, period, quota, or correction. PostgreSQL calculates UTC periods and atomically serializes each user/metric/period with a transaction-level advisory lock before entitlement resolution, idempotency checks, quota enforcement, event insertion and bucket increment. Denied work rolls back without residue. This synchronous path is intentionally bounded; high-volume analytics, exports, credits, organization ownership and provider metering remain separate capabilities.
- Product Onboarding is optional because each SaaS has a different first-success journey. The selected pack exposes one Worker-owned ordered definition, user-scoped versioned PostgreSQL progress, sequential idempotent completion, Product Shell redirect for incomplete `/app` visits, and read-only Admin aggregates. Settings, support, Admin and public/auth routes remain usable while onboarding is incomplete. The neutral welcome step proves the framework only; copied products replace it and increment the definition version before Development release.
- Outgoing Webhooks is an independent optional Cloudflare Queue pack. Product code inserts a bounded event/delivery ledger and awaits Queue acceptance inside its authoritative PostgreSQL transaction; the Queue consumer handles at-least-once delivery through a stable delivery ID, HMAC-SHA256 headers, bounded response capture, explicit retry delays, and terminal failure after five attempts. Endpoint signing secrets are deterministically derived from an environment-only root and endpoint/version, disclosed only on create or rotation, and never stored. User management/history and platform-Admin evidence are read separately. Event vocabulary and product transaction integration remain copied-product release gates.
- Authentication email always passes through `app_auth_email_outbox` and a real provider. CFsend is the default product provider, using a customer-owned Runtime URL, scoped key, verified sender, and stable idempotency key. Resend is an explicit HTTP adapter switch. Cloudflare Email Service is retained as a third opt-in adapter and adds a `send_email` binding only when selected.
- Outbox-only is not an authentication email provider. Missing credentials or provider delivery failure fails closed; Development and Production both require verified email before credential sign-in.
- Operations Health separates liveness from dependency evidence. Public `/api/health` has no PostgreSQL or provider dependency. Better Auth platform Admin `/api/admin/health` actively queries PostgreSQL and exposes only configuration completeness plus bounded persisted evidence for authentication email, each selected Google/GitHub/Apple provider, selected Stripe webhooks, and selected outgoing-webhook Queue deliveries. Unselected optional providers are `not-selected`; selected-but-incomplete configuration and recent terminal delivery failures are `attention`. The read-only dashboard never sends test email, creates Stripe resources, or enqueues product events.
- Theme and locale are user-profile fields exposed through an authenticated preferences contract; product authorization remains separate from these presentation preferences.
- `/support` stores verified-user support and bug submissions in PostgreSQL and limits each account to five new tickets and twenty replies per hour. Users read only their own ticket and public thread messages. `/admin` requires the Better Auth platform `admin` role and uses the official Admin plugin for bounded search, role, ban, unban, session and impersonation behavior rather than duplicating identity SQL. A Better Auth after hook records only successful privileged identity mutations in the append-only audit table; failed authorization produces no audit event. The same Admin shell handles ticket priority/status/admin-only assignment/public replies/internal notes, transactional announcements to verified active users, bounded Overview, and exact-filtered stable-cursor Audit reads. Support attachment metadata may reference the selected Object Storage Pack, but attachment-specific scanning and ticket APIs remain separate product work.
- Baseline PostgreSQL indexes match normalized email lookup, recipient notification reads, global recent-notification counts, support author/time limits, announcement creator/time limits, ticket/status ordering and audit cursors. Product-specific queries still require measured plans before adding indexes.

## Change Spec

Architecture changes require a Change Spec covering the decision, alternatives, compatibility, data migration, rollback, and validation evidence. Update this source before generated `/dp` output.
