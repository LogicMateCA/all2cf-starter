# Project assembler module

Purpose: turn a product brief into a complete SaaS platform plus the smallest owned product-specific module set. The reusable shell and platform services are baseline; the new project should primarily define what its SaaS does.

- After first setup, `AGENT_MAP.md` and `.ai/agent-map.json` route ordinary work to one responsibility domain. `ai:context --task` or `--module` expands only the matched primary files, module docs, checks, Skills and at most three recent relevant Change Specs; `--full` is exceptional.

- `/factory` is the canonical source repository's local creation workspace. It saves an ignored draft and generates a separate Git product with only selected runtime output plus source and materialization receipts. Generated products retain `/setup` for later project configuration. The supervised local service exposes the applicable route and `/dp` on port `15173`; deployed Workers reject both local configurators.
- `ALL2CF_FACTORY.md` defines the future hosted boundary. All2CF wraps this same deterministic engine through asynchronous jobs and typed tools; it does not fork the generator or treat an HTTP request as a build environment.
- `starter-dev` is an everyday least-authority service and has no Docker Socket or Production SSH mounts. Explicit infrastructure/Production work uses the profile-gated `starter-ops` service.
- The reusable visual default is `editorial@2.2.0`, using white/light-gray and black/dark-gray canvases with restrained action color. Setup may replace it during deliberate project initialization, but ordinary feature/configuration edits preserve the saved StyleKit lock; selecting another style must mark the Blueprint dirty and still requires explicit materialization and release.
- Every Setup step owns Save draft and Save and continue behavior; navigation advances only after the Blueprint/config write succeeds. Final save shows a durable completion state instead of navigating to a generic page, and unsaved changes trigger a browser-leave warning. A Vite reload during identity synchronization resumes the saved Setup step.
- Setup Provider calls have bounded timeouts, and slow EAS/identity/DP subprocesses are asynchronous. Blueprint, config and non-empty Provider replacements share one rollback boundary so an error cannot report failure after partially saving the plan.
- Provider cards separate selection from credentials. Installed providers show whether configuration comes from project-local values, the shared development profile, both, or remains deferred. Existing secret values are never returned to the browser; non-empty replacements write only to ignored `.dev.vars`. Each provider includes its official application/configuration links. Google, GitHub and Apple are executable choices.
- Provider verification is explicit and real: social actions open the deployed Better Auth OAuth flow, while CFsend/Resend tests use the same authentication-email adapter and return only non-secret delivery evidence. Cloudflare Email Service waits for its deployed binding. Presence of a key is configuration readiness, not successful-provider evidence.
- Release-platform credentials use the same write-only project/shared/deferred model. Setup verifies the exact Cloudflare account, GitHub identity, EAS project, App Store Connect app or Google Play package without deploying, building or submitting anything.
- The first step captures the SaaS purpose, actors, core objects, tenant model and charging model in the machine-checked `productIntent` block. `/setup` derives an explicit Organization and Billing proposal from those choices; the owner sees and applies the proposal instead of receiving silent package changes.
- The Pages step reads `pages/catalog.json` and selects routes individually. Required auth, legal, docs, home, and 404 surfaces cannot be removed; selecting an optional growth route selects its backing pack, while removing the last route removes that pack.
- Saving a project plan writes the Blueprint and `starter.config.json`, then reuses the transactional identity synchronizer and regenerates `/dp`. A first copied-project identity change must replace canonical Starter resource names.
- `starter.blueprint.json` is the canonical selection and realization record. It distinguishes selected, materialized, locally verified, Development verified, and Production released states.
- `catalog/catalog.json` is the AI-readable internal catalog. Every pack declares targets, ownership, provenance, update policy, requirements, conflicts, performance constraints, verification, documentation impact, and a delivery mode: permanent `baseline`, receipt-backed `materializer`, or unavailable `planned`.
- `catalog/providers.json` inventories all common Provider, Cloudflare infrastructure and release-platform categories. Optional categories always expose `None`; Planned options remain visible but disabled, and only executable options may be selected. Setup and `/dp` consume this catalog rather than maintaining separate prose lists.
- Provider completion is executable: every selectable non-`None` option must declare a verification action, and every external option must include an official setup link. Credential-name contracts cover Turnstile, Expo Push, Twilio and every release platform so Catalog guidance cannot drift from Setup or release scripts.
- Setup uses progressive disclosure: it receives only the 28 StyleKit entries eligible to own a whole-product lock, while the full 146-entry classification remains server-side and in `/dp`. The complete Provider ledger is an Advanced reference rather than a second always-expanded copy of the executable controls.
- `design/catalog.json` is the owned profile layer beneath the Design pack. `/setup` selects one exact profile/version and automatically keeps its backing Design pack consistent; AI consumes the same semantic direction and adapter readiness through project context.
- The shared Design Engine is side-effect-free. `design:contract` compiles all profiles, checks five target adapters, both color modes, reduced motion, dial ranges, distinct profile signatures, pinned donor provenance, and donor-runtime absence before the selected profile can pass repository verification.
- Catalog presets provide the executable `saas-foundation`, Team SaaS, and Custom starting points. Planned packs remain visible but disabled, cannot enter a preset, and are rejected if AI edits the Blueprint directly. A manual deviation from a preset becomes `custom`.
- Materialization is additive and deterministic. `npm run starter:materialize` produces a read-only plan, `starter:materialize:apply` applies selected pack manifests, and `starter:materialize:check` fails on drift. Pack files, page-specific files, dependencies, hard pack requirements, lazy client routes, exact Worker capability routes, generated `run_worker_first` entries, Better Auth server/client registries, optional Worker route/event registries, Queue producer/consumer configuration, secret requirements, generated per-target Design adapters, generated Marketing project data, and lifecycle state share one receipt under `.starter/materialization.json`.
- Deselection is a first-class transition. `/setup` keeps `materialized: true` while changing `selected` to false, clears stale verification/release claims, and lets `/dp` show that removal is pending. Successful apply removes receipt-owned output and then clears the materialized state.
- Removal is ownership-safe: a deselected pack removes only files and exact dependency versions recorded in its receipt. If generated code or a managed dependency changed afterward, removal fails instead of deleting project work. Package installation and source writes roll back on a failed apply.
- Unselected pages, database tables, bindings, secrets, routes, and runtime dependencies are not generated or hidden behind runtime feature flags. Optional pack templates remain in `packs/` as assembler inputs and do not enter the Worker asset graph.
- Database assembly always targets a new empty database. The Blueprint encodes the fixed engine policy (`postgresql`, `sql-first`, `empty`, `selected-pack-baseline`, `out-of-scope`) and separately selects `native-postgresql` or `cfpg`. CFPG Setup accepts exact per-environment All2CF connect commands, stores validated descriptors, and requires different database IDs. Materialization receipt-owns the connector dependency, `pg` alias, `ALL2CF_DATABASE` Service Binding and reversible Hyperdrive replacement. Selecting a pack adds its current baseline SQL before first provisioning; existing-product migrations, backfills and dual writes do not belong to Starter.
- Migration filenames reserve `0001` through `0999` for the permanent baseline and `1001` onward for optional materializer packs. Pack output targets are globally unique even when several independently developed modules are selected together; the migration ledger keys the complete filename and rejects checksum changes.
- Infrastructure reconciliation is environment-scoped: `starter:provision:dev` can create a newly selected Development Queue or R2 bucket without touching Production, while the Production command requires explicit Production intent. The unscoped command is reserved for deliberate first-time all-environment initialization.
- Object Storage is a complete optional materializer path: `none`, native R2, or S3-compatible. It owns its provider adapter, metadata migration, authenticated/public API, Web route, exact binding or dependency/secrets, and removal receipt. R2 has local exact-byte Workerd evidence; a selected real S3 endpoint must pass its own round trip.
- The release controller also reconciles selected R2, Vectorize and Queue identities after Wrangler returns, so automatically provisioned resources enter the environment-scoped ownership ledger before release evidence is recorded.
- Analytics stays unselected in the current Blueprint. The Catalog identifies Pulse as the preferred future external-product contract so AI does not silently add a competing analytics runtime.
- Turnstile is a selectable Better Auth Captcha Pack with separate environment widgets, generated public variables, write-only secrets, a local real Siteverify action, protected credential UI and receipt-safe removal. It remains `None` by default.
- Workers AI is a selectable Cloudflare-native Pack with independent environment model/Gateway configuration, a real local REST test, a generated `AI` Binding, Admin-only deployed test and receipt-safe removal. AI Gateway is an overlay inside this Pack rather than a second conflicting Provider selection.
- Search offers `None`, PostgreSQL and Vectorize. Only Vectorize selects a Pack; it owns isolated index declarations, scoped provisioning, generated Binding/variables, a real round-trip action and safe removal.
- Expo Push uses the same receipt for Worker/Mobile/SQL files, the Expo-compatible dependency, generated native config plugin, environment variables and optional secret requirements. Deselecting it restores an empty optional-mobile-plugin registry.
- Twilio SMS receipt-owns its Worker/SQL files, regional API variable and exact four environment secrets. No SDK dependency is needed; deselection removes the complete channel.
- Cloudflare Images receipt-owns its Worker helper, `IMAGES` Binding and bounded policy variables. Original-file storage remains independently selectable and is never added implicitly.
- Cloudflare Stream receipt-owns its Worker/SQL lifecycle, exact environment variables and two secrets. Selection never implies signed/private playback, because that path is not yet executable.
- Cron receipt-owns its Worker/SQL event feature, exact environment trigger and variables. Empty trigger arrays are intentional removal state, not stale configuration.
- Workflows receipt-owns its Worker feature, generated top-level class export, Binding/resource name, optional schedules and variables. Release state owns exact remote deletion after deselection.
- Durable Objects receipt-owns its Worker feature, generated top-level class export, `STARTER_REALTIME` Binding, declarative SQLite class export and variables. Deselection removes runtime access but never generates a destructive namespace tombstone automatically.
- AI may recommend and prefill selections, but it must show conflicts and consequences before changing the Blueprint. The controller owns integration and release.
- `/dp` is a read-only projection of the Blueprint, Catalog, Markdown contracts, code status, and release evidence. Its lifecycle matrix separates reusable Catalog readiness and delivery mode from the current Blueprint's selected, materialized, locally verified, Development verified, and Production released states. It never edits the Blueprint.

StyleKit is the pinned design-source library for an owned global style snapshot. Its entries are classified as global systems, layouts, enhancements or reference-only sources; only the first category may own the base style lock. PowerAI is the pinned complete page/content donor. Open SaaS is the pinned product-shell/flow donor, SaaSBoard is the pinned authenticated-shell interaction donor, and LastSaaS is the pinned completeness checklist. MapCN remains a capability donor; Open Design and RunCopilot remain research/extraction aids. Donor runtimes never enter generated products. Better Auth core and every selected official plugin, including Organization, API Key, Passkey, 2FA, Expo and Stripe, are the tracked stable-compatible upstream family.

The `saas-foundation` preset is now the default executable baseline. `catalog/saas-sources.json` pins the three SaaS donors and accepted adaptation paths; `catalog/saas-capabilities.json` tells AI what is baseline, materializer-owned, or planned and which routes, APIs, schema, verification, and gaps belong to each capability. The 146-entry StyleKit source is fully classified: 28 deliberately distinct whole-product systems are selectable through committed immutable `2.2.0` snapshots, nine active owned compiler families and optional signature layers; 35 close variants, 18 layouts, one Admin density mode and enhancements remain separately composable. The Neumorphism acceptance slice, refreshed 28-cover Setup selector and complete PowerAI growth-page families passed their recorded browser scopes; the current Editorial selection remains a separate visual gate. Active Change Specs stay visible in `/dp` until remaining provider and release evidence is complete.

Google, GitHub and Apple are executable social login choices. Setup may select any combination and shows exact Development/Production callback URLs plus official application links. Identity synchronization writes only the selected Provider names and secret requirements into both Wrangler configs; deferred credentials remain visible blockers rather than fake enabled buttons.

The materializer is locally verified through complete MapCN and Better Auth SaaS pack select, plan, apply, empty-schema, workerd, build, check, deselect, safe-removal, and dependency-absence cycles. Organization-only, Stripe-only, TOTP-2FA-only, Entitlements, Usage, API-Key-only, Onboarding-only, Outgoing-Webhook-only, and the full API SaaS composition pass focused cycles. The 2FA cycle proves pending enrollment, TOTP activation, challenged password sign-in, one-time recovery codes, recovery rotation, disablement, audit and notification evidence. The API SaaS cycle proves hard dependency closure, key scope and owner isolation, no API-key sessions, idempotent quota use, exact 429 exhaustion, signed Queue events, revoke denial, lazy Developer UI and Starlight reference. The Webhook cycle proves generated Development/Production Queue ownership, one-time derived secrets, exact HMAC envelopes, 2xx success, non-2xx retry-to-success, five-attempt terminal failure, user isolation, Admin readback, disposable empty-database workerd execution, receipt-safe removal, and a clean default regression. Baseline Operations Health is checked in default, Stripe-only, and Outgoing-Webhook-only workerd flows so optional provider and Queue state comes from selected configuration and persisted evidence rather than placeholders. Design switching and optional Growth route selection/removal passed current real browser acceptance. The selected StyleKit adapter, reusable Page packs and MapCN capability are locally verified; a copied product still owes truthful content, metadata, forms and product evidence. `/setup` still saves intent rather than running commands itself; AI must show the plan and invoke apply.

For local runtime acceptance, `npm run dev:worker` is the canonical Worker command: it reads `.dev.vars` without printing secret values and maps Hyperdrive to the Development database coordinates in `starter.config.json`. Public Worker, authenticated disposable-database, and local-only Setup browser modes run from the pinned Compose QA profile. `/setup` must remain absent from deployed Workers.
